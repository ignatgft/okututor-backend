# Search Performance (Okututor Backend)

## Цели (спека #28)

- p50 < 200 ms, p95 < 500 ms при 50 RPS;
- поиск без внешних обязательных зависимостей;
- наблюдаемость: structured timing-логи.

## Замер на локальном стенде (этап 6)

Стенд: PostgreSQL 16 (Docker), ~10 курсов, Windows, одна нода.

| Метрика | Значение |
|---|---|
| 120 HTTP-запросов (RU/EN/фильтры/каталог) | **p50 = 9.3 ms, p95 = 18.9 ms, max = 28.9 ms** |
| Серверная часть (SEARCH-лог: db+ranking) | 2–3 ms |

Цели p50/p95 превышены с большим запасом. Замер включает сетевой round-trip
локального curl; k6-прогон на целевой инфраструктуре выполняется скриптом
`k6/search-load-test.js` (thresholds p50<200/p95<500 при 50 RPS).

## Планы запросов (EXPLAIN ANALYZE, 5000 курсов)

- Каталог `WHERE status='APPROVED' ORDER BY average_rating DESC NULLS LAST,
  created_at DESC LIMIT 20` → **Index Scan using idx_courses_approved_rating_created**,
  ~0.09 ms.
- FTS-кандидаты → Bitmap по `idx_courses_status` + фильтр tsquery при малой доле
  APPROVED; при селективном запросе планировщик выбирает GIN по векторам
  (cost-based). На малых таблицах Seq Scan оптимален и ожидаем.
- `lower(title) % token` — trgm GIN `idx_courses_title_lower_trgm` доступен
  планировщику; при малом числе APPROVED строк дешевле bitmap по статусу.

## Наблюдаемость

Каждый запрос пишет structured-лог:

```
SEARCH query_length=.. candidate_count=.. result_count=.. total=..
normalization_ms=.. db_ms=.. ranking_ms=.. total_ms=..
```

## Что даёт каждая оптимизация

| Оптимизация | Эффект |
|---|---|
| DTO-проекция + JOIN teacher | устранён N+1, entity-граф не загружается |
| SQL-пагинация каталога по id | нет in-memory пагинации (HHH000104) |
| `to_tsquery` + префиксы | индексное FTS-ранжирование вместо LIKE/`plainto_tsquery` |
| парциальный индекс каталога | Index Scan для самого частого запроса |
| батч availability/personalization | константное число запросов независимо от пула |
| candidate-limit | ранжирование ограничено 100 кандидатами при любом объёме данных |

## Риски и пределы

- Глубокая пагинация за пределами candidate-limit (страницы дальше 100 лучших)
  не отдаются — осознанный trade-off кандидатской архитектуры (спека #13).
- Синоним-regex по `description` не индексирован; при росте каталога >10k курсов
  перенести матчинг синонимов в FTS-словарь/thesaurus (V19+).

## Кэширование (спека #17) — решение: не добавлять

Измерения (локальный benchmark, 120 запросов, пул 100 кандидатов):

| Метрика | Значение |
|---|---|
| p50 | 9.3 мс |
| p95 | 18.9 мс |
| max | 28.9 мс |
| SQL-запросов на поиск | 2 (candidates + count) + 1 батч availability + 1 батч personalization |

Поиск уже укладывается в p95 < 20 мс; узкое место не БД, а сеть/сервлет.
Redis в проекте есть, но добавление кэша поиска сейчас даст < 10 мс экономии
ценой инвалидации при каждом изменении курса/слотов/бронирований.

**Стратегия (если понадобится):** кэш только anonymous-запросов
`search:courses:{hash(q+фильтры+page)}` TTL 30–60 c, инвалидация по событию
(курс изменён/забронирован слот). Персонализированные запросы не кэшировать.
Порог включения: p95 > 100 мс или DB load > 50% на пике.
